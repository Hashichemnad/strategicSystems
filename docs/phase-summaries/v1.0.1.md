# Release 1.0.1 — Salesforce standby sync fixes from real-sandbox testing: summary

Status: **built — awaiting owner acceptance** · version **1.0.1** (`deploy/VERSION`, `Directory.Build.props`). Scope: the four defects found
when the Phase 23 standby sync ([`docs/SPEC-ADDENDUM.md`](../SPEC-ADDENDUM.md) §G) was tested against a real Salesforce sandbox, plus one
defect the new tests found. Design note updated: [`docs/design/salesforce-sync.md`](../design/salesforce-sync.md). Decisions: ADRs
**0210–0214** (proposed). Guides: [`en`](../guides/en/salesforce-sync.md) · [`ar`](../guides/ar/salesforce-sync.md). Create the tag on the
merged commit of `main`: `git tag -a v1.0.1 -m "Integrated Strategy System 1.0.1" && git push origin v1.0.1`.

## Tests
- **Fake org made realistic** (`src/Host/Strategy.Host/Infrastructure/MockSalesforceOrg.cs`): `User` describe **recorded from the live org**
  through the Salesforce connector (179 fields, no `IsDeleted`; field shapes only) and `Contact` from the standard object reference plus
  `Employee_Number__c` (the connector available could not describe Contact) — `Infrastructure/SalesforceDescribes/*.json`, embedded; unknown
  columns answer HTTP 400 `INVALID_FIELD` (also at Bulk job creation); `Sforce-Limit-Info` on every answer; `/limits` refusal switch; real
  relationship fields on `ProcessInstance`, `ProcessInstanceStep` and `…__History`. The 1.0.0 queries (`SELECT Id, IsDeleted, … FROM User`,
  `… EmployeeNumber … FROM Contact`) are refused by this fake org as by Salesforce, so CI catches this class of error.
- **Unit** (`tests/Strategy.UnitTests/Integration/SalesforceSandboxFixesTests.cs`): limits refusal codes, usage header parsing,
  reserve table, stored 1.0.0 limits still readable, error parsing in every body shape, call sanitising (no token, no filter literals),
  picklist → whole number / number / ratio, unconvertible and unmapped values, `FieldsOf` with User / Contact describes, `SyncQueries` lists,
  the shipped pack.
- **Integration** (`SalesforceSyncTests`, 7 new): limits refused (test warning, run with header usage, stop at 95 % usage, back to `/limits`);
  stored error details (INVALID_FIELD, `invalid_grant`, no secrets anywhere); risk picklists → numbers with *Validate* warning / error;
  *Validate* of people, template, approval relationship and watermark fields, inactive user not deleted; unknown persons resolved by bulk
  re-process (people first) and by the next run after the contact fix; every sync target referenceable; pack 1 → 2 upgrade keeps an edited
  object. `MockSalesforceDemoTests`: the Development demo org validates the E2E objects and runs a full load without Salesforce errors.
- **Web** (Vitest): `SalesforceErrorDetails` / `ServerMessage` in AR and EN, the `/limits` warning, worded usage and target kinds; every
  server message key (now incl. `integration.sync.warnings.*`) translated.
- Existing suites unchanged and green; the version test expects 1.0.1 with its release notes first.

## Decisions taken
ADR 0210 (limits from the usage header), 0211 (error details), 0212 (describe-driven queries, full validation, picklist → number, bulk
re-processing order), 0213 (shipped pack upgrade), 0214 (sync targets referenceable). No deviation from the SPEC.

## Known gaps
- The live `PMS_Project_Risk__c` describe read through the connector did not list `Risk_Owner__c` (mapped by the pack). It may be hidden by
  field-level security for that user; *Validate* now reports it on the customer's org. Owner to confirm the field and its access.
- The demo org (Development) derives field types of objects other than User / Contact from the pack as text, so its date / number kind checks
  are only meaningful for the objects the E2E spec uses; the real describe applies them everywhere.
- A people exception recorded before a new match field was configured holds no value for that field: it resolves at the next run (which reads
  the field), not by re-processing its stored payload.

## How to demo
1. Development with `Development:MockSalesforce=true`: Settings → Integrations → Salesforce sync → Connection → *Test connection* (works).
2. In a test, `MockSalesforceOrg.RefuseLimits = (Forbidden, "INSUFFICIENT_ACCESS")`: the test shows *"The connection works, with warnings"*
   with the Salesforce answer; runs continue and the API usage bar says "from Salesforce's response headers".
3. Break a mapping (e.g. an external-ID template field that does not exist) → *Validate* names the field, object and usage; a run against a
   field removed later shows `INVALID_FIELD` with the call and Salesforce's message in the run log.
